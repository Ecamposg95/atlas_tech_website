Propósito y uso

Este documento es la referencia de ingeniería de Atlas ONE: describe cómo está construido el sistema que opera DASIC, dónde vive cada responsabilidad y qué condiciones no pueden romperse al modificarlo. Sirve para tres cosas: incorporar a alguien nuevo al código, auditar una decisión antes de tomarla, y verificar el estado de la base de datos contra lo que el sistema declara.

Criterio editorial

Todo lo que se afirma aquí es verificable en el repositorio. Cuando algo es intención y no comportamiento implementado, se dice explícitamente. Cuando algo es deuda conocida, se nombra como tal en lugar de describirse como diseño.

01
Forma del sistema

Arquitectura

Atlas ONE es un monolito FastAPI + PostgreSQL que sirve su propia SPA de React 18. Un único proceso atiende la API bajo /api/*, los assets estáticos y el index.html del build para toda ruta /spa/*. No hay gateway, ni cola, ni servicio auxiliar: el despliegue es una unidad y la frontera entre capas es una convención de código, no de red.

Navegador
SPA React 18
Vite · TS · Tailwind. Sesión por cookie JWT.
Proceso
FastAPI · Python 3.11
Routers /api/*, seguridad con can(), dominios router·service·repository.
Servicios
Lógica sensible
Folios, stock, cobranza, FX, documentos, IA.
Datos y externos
PostgreSQL · 47 tablas
Banxico (SIE), SMTP, Anthropic.
Un solo proceso sirve la API y la SPA; la lógica sensible vive en servicios, no en los routers.
Secuencia de arranque · app/main.py → app/core/lifespan.py → app/db/seeds.py
Configuración
configure_logging() y get_settings() cachean y validan DATABASE_URL y SECRET_KEY: la app se niega a arrancar sin ellas. normalize_database_url reescribe postgres:// → postgresql+psycopg://.
Esquema
El lifespan ejecuta Base.metadata.create_all() —transicional— y run_all_seeds(). Dentro, run_backfill_ddl aplica ALTER TABLE … ADD COLUMN IF NOT EXISTS de forma idempotente para esquemas legacy: el deploy no ejecuta Alembic, así que este backfill es el camino real a producción.
Datos base
Seeds de superadmin, marcas, catálogos SAT, contactos principales, pipeline por defecto y unidades. Son idempotentes por diseño: arrancar dos veces no duplica catálogo.
Servicio HTTP
Routers montados bajo /api/*; toda ruta /spa/* devuelve el index.html del build commiteado en app/static/dist/.
Consecuencia operativa

Como el esquema se materializa en el arranque, el estado de la base depende del orden de despliegues, no solo del historial de migraciones. Cualquier columna nueva debe existir en los dos lugares (revisión Alembic y _BACKFILL_DDL) o el ambiente quedará divergente sin error visible.

Atlas ONE · DASIC IndustrialAutenticación y permisos
01

Autenticación, permisos y alcance del producto

Dos mecanismos de autorización coexisten. Saber cuál está en juego en el archivo que se toca es requisito para no abrir un hueco de permisos.

MecanismoComportamiento y estado
SesiónJWT (python-jose) en cookie HttpOnly access_token. La API acepta además Authorization: Bearer. El login es la única página Jinja que sobrevive, en la raíz /.
Matriz declarativa
mecanismo preferido
app/security/permissions.py: can(user, action, resource) y require(...), con variantes :own y scope_query_by_owner() para acotar consultas al dueño del registro. Es el mecanismo que usa app/domains/remisiones/ y el que debe usar todo código nuevo.
Helpers históricos
deuda conocida
app/security/jwt.py (allow_admin, allow_all_staff, …) sigue vigente en la mayoría de routers. Migrar un router a la matriz es una mejora bienvenida al tocarlo; hacerlo de golpe no es requisito.
Decisión de producto · mono-empresa

El sistema es mono-empresa, dedicado a DASIC. Decisión del 19 de agosto de 2026.

Qué se retiró
El esquema multi-tenant, en la migración 20260429_01_drop_multitenant.
Qué quedó
organization_id sobrevive como columna inerte en 5 tablas y no implica aislamiento. Filtrar por ella no es una barrera de seguridad.
Qué es configuración
branding.ts y platform_config son parámetros en runtime, no multi-tenancy.
Implicación de diseño
El aislamiento de datos que hoy importa es por usuario y rol (:own), no por organización.

02

Decisiones de arquitectura

Seis decisiones explican la mayor parte de la forma del sistema. Se registran con su contexto, su consecuencia y el costo que dejan abierto, para que una decisión futura no reabra lo ya resuelto sin saberlo.

ADR-01
Un proceso sirve la API y la SPA
A favor
Un artefacto que desplegar, sin CORS ni coordinación de versiones entre API y cliente: el build vive en app/static/dist/.
Costo
API y frontend escalan juntos y comparten ciclo de vida; un error en el arranque deja al usuario sin interfaz, no solo sin datos.
ADR-02
Mono-empresa: se retira el multi-tenant
A favor
Elimina un eje de complejidad que nadie usaba: consultas, permisos y seeds dejan de arrastrar el filtro por organización.
Costo
Reintroducirlo sería un cambio de esquema mayor. Mientras tanto, organization_id queda como columna inerte que puede confundir a quien la lea sin contexto.
ADR-03
Backfill DDL idempotente en el arranque, no Alembic en el deploy
A favor
Tolera esquemas legacy y ambientes desalineados: ADD COLUMN IF NOT EXISTS converge sin intervención manual.
Costo
El historial de 54 migraciones deja de ser la única verdad del esquema. Obliga a la regla de migración doble (§12) y no cubre cambios destructivos ni backfills de datos.

Atlas ONE · DASIC IndustrialDecisiones de arquitectura
ADR-04
Permisos como matriz declarativa
A favor
La autorización se lee en un solo archivo y admite alcance por dueño (:own, scope_query_by_owner()) sin repetir condiciones en cada router.
Costo
Convivencia con los helpers históricos: hoy hay dos formas de responder “¿puede este usuario?”. Mientras dure, revisar ambas al auditar un endpoint.
ADR-05
router · service · repository para código nuevo
A favor
app/domains/remisiones/ demuestra el patrón: el router valida y traduce HTTP, el service concentra reglas y transacciones, el repository consulta. Las plantillas Jinja viven en archivo, nunca en HTML inline.
Costo
Dos estilos en el mismo repositorio: 24 routers planos frente a un dominio estructurado. Migrar tiene costo y no hay plazo; la regla es no crear nuevos routers planos.
ADR-06
Cálculo sensible siempre en el servidor
A favor
Folios, totales y stock se resuelven en servicios del backend. El cliente puede equivocarse sin corromper el documento ni el inventario.
Costo
Una excepción deliberada: el tipo de cambio direccional se implementa en espejo (calc.ts ↔ ventas.py) para que el cotizador dé retroalimentación inmediata. Ese espejo hay que mantenerlo a mano.
Cómo usar esta sección

Antes de proponer un cambio estructural —separar el frontend, reintroducir organizaciones, mover cálculo al cliente, adoptar Alembic en el deploy— conviene contrastarlo con la decisión que lo cubre y con su costo declarado. Si el cambio sigue teniendo sentido, lo que corresponde es sustituir la decisión, no ignorarla.

04

Mapa del frontend

La SPA vive en web/: React 18 + Vite 5 + TypeScript + Tailwind + shadcn/ui + Zustand + TanStack Query v5. Cada pantalla es una feature con anatomía uniforme, de modo que ubicar código no requiere leer el árbol completo.

types.ts
La vista que la feature necesita de los contratos del backend.
hooks/
Acceso a datos con TanStack Query; sin fetch disperso en componentes.
pages/
Composición de pantalla y ruteo.
components/
Piezas propias de la feature, no compartidas hacia afuera.
25 features
analitica auth borradores catalogos clientes compras contactos cotizador crm cxc dashboard fantasmas fx gastos inventario precios recordatorios remisiones reportes reportes_servicio reportes_servicio_docs seguimiento servicios superadmin usuarios
Compartido
Primitivas del design system en web/src/components/ui/ con tokens semánticos y cero colores crudos; componentes documentales en web/src/components/document/; API, permisos y branding en web/src/lib/.
Build
npm run build genera app/static/dist/, que se commitea: ese directorio es el frontend que sirve producción. Un cambio de UI sin build commiteado no llega al usuario.

Atlas ONE · DASIC IndustrialInvariantes y reglas
07

Invariantes y reglas de negocio

Condiciones que deben cumplirse después de cualquier operación. Se enuncian con su punto de verificación en datos, porque una invariante sin forma de comprobarse no es una invariante.

INV-01
Los folios son únicos y consecutivos, y se emiten solo en el backend. folio_service.generar_folio combina advisory lock, MAX(folio) y regex con formato COT-YYYYMM-INICIALES-NNNN / VTA-….
Verificación: ordenes_venta.folio y remisiones.folio son únicos e indexados; ningún folio se calcula en el cliente.
INV-02
Subtotal, IVA y total se recalculan en el servidor al guardar. El precio se forma como costo + utilidad, no como lista − descuento.
Verificación: ordenes_venta.total nunca proviene del payload del cliente.
INV-03
Toda mutación de inventario deja rastro. stock_service.aplicar_movimiento es la única puerta a productos.stock_actual y escribe movimientos_stock con stock_resultante.
Verificación: el último stock_resultante por producto coincide con productos.stock_actual.
INV-04
Disponible = stock − reservas activas. Las reservas se crean al guardar la cotización y se liberan o consumen al cancelar o convertir.
Verificación: movimientos de tipo reserva y liberacion se cierran por par; una reserva huérfana bloquea stock que nadie va a entregar.
INV-05
El stock se descuenta una sola vez por remisión. remisiones.stock_descontado (boolean, default false) es la bandera de idempotencia del descuento.
Verificación: no debe existir una remisión con stock_descontado en false y movimientos de salida asociados, ni lo contrario.
INV-06
La remisión conserva su origen y no altera la cotización. remisiones.orden_venta_id enlaza la entrega con la venta y cada línea guarda detalles_remision.detalle_orden_id; la cantidad es numeric(12,3) para permitir parciales.
Verificación: la suma de cantidades remitidas por detalle_orden_id no excede la cantidad cotizada, salvo sobre-entrega autorizada.
INV-07
Entregar más de lo cotizado exige autorización nominal. remisiones.sobre_entrega_autorizada_por_id apunta al usuario que la autorizó; sin ese registro, la sobre-entrega no debe existir.
Verificación: excedente ⇒ columna poblada. Es la regla de dominio referida como BR-05 en el service de remisiones.

INV-08
El tipo de cambio protege a DASIC en ambas direcciones. USD→MXN usa DOF más tolerancia; MXN→USD usa DOF menos tolerancia. La orden guarda tipo_cambio, tc_mn_a_usd, tc_usd_a_mn y tolerancia_tc.
Verificación: la implementación está en espejo, calc.ts::resolveDirectionalTcs ↔ ventas.py::_resolve_directional_tcs. Tocar uno obliga a tocar el otro.
INV-09
El TC del día se resuelve una vez y se cachea. fx_service guarda en tipos_cambio_dia; la fuente es Banxico SIE (serie SF63528) con fallback público.
Verificación: una cotización histórica se relee con el TC que tenía, no con el de hoy.
INV-10
El saldo del cliente se mueve solo por transacciones. Cargos y abonos viven en transacciones_clientes con estatus_pago y monto_pagado; la cobranza aplica pagos en FIFO y calcula aging 0-30/31-60/61-90/90+.
Verificación: clientes.saldo_actual debe reconstruirse desde el rastro de transacciones.
INV-11
Las cantidades en documentos se formatean en un solo lugar. formato.py::fmt_cantidad impone máximo 2 decimales sin ceros colgantes, aunque la columna sea numeric(12,3).
Verificación: ningún template ni componente formatea cantidades por su cuenta.
INV-12
La sesión no se mueve al cliente. El JWT viaja en cookie HttpOnly; el frontend no lee ni almacena el token.
Verificación: no hay token en localStorage ni en estado de la SPA.
INV-13
Toda columna nueva existe en dos lugares. Revisión Alembic en migrations/versions/ y entrada en _BACKFILL_DDL (app/db/seeds.py), porque el deploy no corre Alembic.

Estados de la remisión

Los cuatro valores de EstadoRemision y las columnas que cada transición escribe. Las transiciones permitidas las decide app/domains/remisiones/service.py: el diagrama muestra el efecto en datos, no una máquina de estados declarada en el modelo.

Columnas involucradas: estado · emitida_at · emitida_por_id · stock_descontado · recibido_por · recibido_at · cancelada_at · cancelada_por_id · motivo_cancelacion
1
Emitir. Escribe emitida_at y emitida_por_id, marca stock_descontado y registra movimientos de salida con stock_resultante. Es el único paso que toca inventario, y solo una vez (INV-05).
2
Recibir. Escribe recibido_por y recibido_at; el transportista queda en el documento. No vuelve a mover stock.
3
Cancelar en borrador. No hubo descuento de stock: solo se registran cancelada_at, cancelada_por_id y motivo_cancelacion.
4
Cancelar emitida. El stock ya salió: la reversión debe quedar como movimiento nuevo, nunca borrando el original. Verificar contra stock_descontado antes de asumir el estado del inventario.
La sobre-entrega no es un estado: es una condición sobre las cantidades que exige sobre_entrega_autorizada_por_id (INV-07).

Glosario de dominio

Términos tal como los usa el sistema. Cuando el nombre de negocio y el nombre en base de datos no coinciden, se indican ambos.

Cotización
Documento comercial en ordenes_venta; su estado inicial es cotizacion y comparte tabla con la venta.
Remisión
Documento de entrega en remisiones; puede ser parcial y conserva el vínculo con la cotización.
Folio
Identificador legible y consecutivo del documento, emitido por folio_service.
Entrega parcial
Remisión que cubre parte de una partida; la cantidad es numeric(12,3) y deja saldo pendiente.
Sobre-entrega
Entrega por encima de lo cotizado; requiere sobre_entrega_autorizada_por_id.
Reserva
Movimiento de stock que compromete existencias sin sacarlas del almacén.
Disponible
Stock menos reservas activas. Es el número que puede prometerse a un cliente.
Kardex
Historial de movimientos_stock por producto, con stock_resultante en cada fila.
Producto fantasma
Línea vendida fuera de catálogo, con seguimiento a OC y posible promoción a producto.
Costo-first
El catálogo parte de costo_compra y moneda_compra; los precios se derivan de ahí.
TC direccional
Dos tipos de cambio por documento según el sentido de la conversión, con tolerancia sobre el DOF.
Tolerancia TC
Margen aplicado al TC de referencia; se guarda en la orden (tolerancia_tc).
CxC
Cuentas por cobrar: cargos abiertos de un cliente y su antigüedad.
Aging
Clasificación de saldos por antigüedad en cubetas 0-30 / 31-60 / 61-90 / 90+.
FIFO
Criterio de aplicación de pagos: primero el cargo más antiguo.
Deal
Oportunidad del CRM ubicada en una etapa de un pipeline; puede apuntar a una cotización.
Base instalada
Equipos del cliente registrados en activos_instalados, opcionalmente ubicados en una planta.
Backfill DDL
Bloque idempotente de ALTER TABLE … IF NOT EXISTS que converge el esquema en el arranque.
Seed
Carga inicial idempotente: superadmin, marcas, catálogos SAT, pipeline por defecto, unidades.
Advisory lock
Candado de PostgreSQL usado para serializar la emisión de folios.
Fusión de empresas
Deduplicación de clientes; queda registrada en cliente_merge_log, sin FK a propósito.
Tokens semánticos
Variables de color y tipografía del design system de la SPA; no se usan colores crudos.
